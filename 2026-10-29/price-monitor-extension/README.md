# 皮肤套餐监控（Edge / Chrome 扩展 · 第五人格藏宝阁）

藏宝阁页面监控扩展，两种模式可切换：

- **皮肤套餐模式**：扫描账号卡，当你指定的皮肤出现在这个账号里、且这些皮肤的参考价合计 < 阈值时，推送企微。
- **搜索比价模式**：按你设的关键词周期搜索（价格升序），当某关键词最低价 ≤ 该词目标价时，推送企微。每个关键词可单独写「关键词,目标价」，不写则用全局默认目标价。

> 关键约定：**皮肤名与参考价由你用 Excel/CSV 提供**（价格来自你的清单，不在页面上取）。页面只负责“这个账号拥有哪些皮肤（按名字）”。搜索模式则直接读搜索结果的最低价。

## 功能
1. **自动刷新（带随机抖动）**：实际间隔 = 基础间隔 + 0~抖动 秒随机数，避免固定节奏被风控识别。
2. **时段控制**：仅在设定的时段内扫描/搜索；时段外静默空转，不碰服务器。
3. **数据判断**：
   - 套餐模式：账号卡内提取皮肤名 → 与清单匹配 → 累加参考价 → 合计 < 阈值 即命中。
   - 搜索模式：周期跳转到关键词搜索结果（价格升序）→ 读出所有 ≤ 目标价的商品 → 每个商品单独判重 → 有新品命中即提醒。
4. **消息提醒**：命中后推送企微 + 本地通知；通知内附**可点击的商品链接**，点一下直接进商品详情页；同一商品同一价位只提醒一次，不同商品即使价格相同也会各自提醒（v0.20.1 起）。

## 快速上手（一步一步，给非技术的你）
当前默认就是「搜索比价」模式，且已经帮你预填了 3 个皮肤，你基本零配置就能跑：

1. **装扩展**：打开 `edge://extensions` 或 `chrome://extensions` → 右上角开「开发人员模式」→「加载解压缩的扩展」→ 选本目录 `price-monitor-extension/`。
2. **开配置**：点工具栏里的扩展图标 →「打开配置」。
3. **填 Webhook**（唯一必填）：把企业微信机器人的 Webhook 地址粘到最下方的「企业微信机器人 Webhook 地址」框。没有它无法推消息。
4. **启用**：勾上「启用监控」→ 点「保存并应用」。
5. **开着页面**：在你的 Chrome 里打开藏宝阁任意页面（保持这个标签页在前台）。扩展会自动注入，按随机间隔轮流搜索 3 个皮肤，命中就推企微 + 弹本地通知（带可点链接）。你不用点任何东西。

> 那 3 个皮肤（`于此岸赴宴,300` `蜃景,1000` `赤宴,1200`）已经在配置里了，数字就是各皮肤「最低价目标」——搜索结果最低价 ≤ 该数就提醒。所以第 1~5 步之外你什么都不用动。

### 价格表（Excel/CSV）和扩展是什么关系？
- 我给你的 `skin-monitor-list.xlsx` 只是一个**外面的表格文件**，方便你查看/编辑价格；扩展并不会自动读它。
- 扩展内部自己存了一份同样的数据（就是配置页里的「关键词」框）。所以现在**不需要导入**也能跑。
- 以后你想改清单：直接编辑 Excel →「另存为 CSV（逗号分隔）」→ 在配置页用上方「批量导入清单」选这个 CSV 即可；它会按当前模式填进对应框（搜索模式进「关键词」，套餐模式进「皮肤清单」）。
- 嫌麻烦也可以直接在配置页的框里**手动改文字**（每行 `名称,数值`）。

## 配置项白话说明
- **启用监控**：总开关。不勾就不注入、不扫描。
- **监控页面地址**：扩展往哪些网址注入脚本。默认 `https://id5.cbg.163.com/*` 已覆盖藏宝阁，一般不用改。
- **监控模式**：「搜索比价」= 每个关键词单独搜、看最低价（你当前用的）；「皮肤套餐」= 一个账号里指定皮肤合计价低于阈值才提醒。
- **基础刷新间隔 / 随机抖动**：两次操作之间等的秒数 = 基础间隔 + 0~抖动 的随机数。默认 60 + 30，即 60~90 秒一次，**故意不固定**以免被风控。想更保守就调大。
- **整页刷新**：套餐模式才用（刷新整个页面）；搜索模式始终按关键词跳转，此项无效。
- **启用监控开关**：工具栏弹窗里也有一个同名开关，可随时暂停/恢复，无需进配置页。
- **时段控制 / 起止**：只在某个时段内干活，时段外只静默等待。默认 9→23 点。比如你只想夜里跑，就设 22→8。
- **商品链接选择器**：命中通知里那个「点此查看」链接从哪取。默认自动取卡片里的第一个链接，一般不用改。
- **搜索关键词**：每行一个 `关键词` 或 `关键词,目标价`。如 `赤宴,1200` 表示搜赤宴、最低价 ≤1200 提醒。当前已预填 3 个。
- **搜索 URL 模板**：搜索用的网址，`{keyword}` 会被替换成关键词。默认已拼好（按价格升序），一般不用改；若你的链接必须带 `refer_sn`，把完整链接粘来、把关键词位置换成 `{keyword}`。
- **最低价目标**：全局默认目标价，仅当某关键词没写 `,目标价` 时兜底。
- **最低价所在元素选择器**：取最低价用哪个页面元素。默认 `.row-hd .price`，一般不用改。
- **企业微信 Webhook**：推消息的地址（必填）。
- **套餐模式专用**（切到套餐才出现）：皮肤清单（每行 `皮肤名,参考价`）、合计阈值、各选择器——用于"一个账号里多个皮肤加起来便宜"的场景。

## 启用后会发生什么（搜索模式）
1. 你点开启的一瞬间（约 1 秒内），标签页就跳到第一个关键词的搜索结果页。
2. 首轮把清单里每个关键词依次快速走一遍（每个约 1.5 秒间隔，只为等页面渲染）。
3. 首轮走完后，才进入「基础间隔 + 抖动」的随机轮询（默认 60~90 秒一轮）。
4. 只要你把标签页切回列表页/首页，它会立刻重新去搜，不会傻等间隔。
5. 停在商品详情页时不会被打扰，不会被强制跳走。

> 嫌首轮太快、想全程都按慢速间隔跑，可在配置页勾选「每轮都等待随机间隔」。

## 搜索比价模式原理
藏宝阁筛选是**服务端 URL 参数驱动**：`/cgi/mweb/pl?keyword=赤宴&order_by=price%20ASC` 即“搜索赤宴并按价格升序”。扩展在标签页内周期性 `location.href = 搜索URL(下一个关键词)`，页面加载后读出结果列表里所有 ≤ 该词目标价的卡片（第一个卡片的最小值用于行情/补货判定），逐商品做去重后推送。

## 风控策略（重点）
- **随机抖动**：`实际间隔 = 基础间隔 + Math.random()*抖动`。
- **时段控制**：`inWindow()` 判断当前小时是否在窗口内；时段外不刷新、不搜索、只静默等待。
- **搜索模式低侵扰**：单个标签页轮换跳转，每次只在窗口内、按随机间隔导航一次。
- 建议基础间隔 ≥ 60s；网易藏宝阁风控严格，若页面要求验证先手动通过。

## 停摆报警只在工作时段内发出（v0.20.0）

之前有个明确的误报：**时段外停摆也会报警**。比如你设了 9:00–23:00，凌晨 3 点监控本来就不该工作，但保活模块照样推「监控已停摆」——这是噪音。

现在报警前先判断时段：

| 情况 | 行为 |
|---|---|
| 当前**不在**监控时段内 | 静默，不报警（停摆属正常） |
| 当前在时段内，**刚进入不到 15 分钟** | 静默，给页面恢复时间 |
| 当前在时段内，超阈值无新查询 | 报警「已超过 N 分钟没有新的查询记录（当前在监控时段内）」 |
| 当前在时段内，但标签页被关 | 报警「监控页面已被关闭」 |

**跨午夜时段正确处理**：设 22 → 8，凌晨 3 点仍算时段内，正常报警；中午 12 点算时段外，静默。

**宽限期不会掩盖真异常**：如果进入时段后一次都没成功查询过（例如上班了但页面一直没打开），即使还在 15 分钟内，也会正常报警——因为这不是"还没来得及跑"，而是"从一开始就没跑起来"。

### 停摆阈值改为跟随配置

原来固定 60 分钟，皮肤多或周期长时会误报。现在按「整轮周期 + 轮内间隔」动态计算：

```
阈值 = max(60, min(180, 一轮耗时 × 2.5))
```

实例：
- 3 个皮肤 / 30 分钟周期 → 阈值约 **88 分钟**
- 30 个皮肤 / 1 小时周期 → 阈值约 **175 分钟**
- 上限 180 分钟，避免配置异常导致长期不报警

### 💰 蜃景 · 低于目标价 ¥900

## 推送策略调整（v0.18.0）

**补货 / 卖出不再实时推送**，只在每天 **0:00** 汇总一次。

### 什么时候会给你发消息

| 情况 | 是否推送 |
|---|---|
| 出现**低于目标价**的价格 | ✅ 立即推送 |
| 只是补货（没到目标价） | ❌ 不推送，记入当日流水 |
| 只是卖出（价格变高） | ❌ 不推送，记入当日流水 |
| 每天 0:00 | ✅ 推送昨日汇总 |

这样微信里只有两种消息：**"可以下手了"** 和 **"昨天的总结"**。

低于目标价的消息：

```
### 💰 低于目标价提醒
**关键词**：赤宴
**最低价**：¥1800（目标 ≤ ¥1900）
**商品链接**：[点此查看](...)
https://id5.cbg.163.com/cgi/mweb/equip/1/...
```

如果同一轮既低于目标价又伴随补货，会多一行“🆕 同时检测到补货”，但仍然只有一条消息。

### 每天 0:00 的汇总长这样

```
### 📊 昨日补货 / 卖出汇总（2026/10/30）

**总计**：补货 2 次，卖出 2 次

**赤宴**（当前最低 ¥1800）
- 🆕 补货 2 次，最低到 ¥1700
  · 10:00:00 ¥2000 → ¥1800
  · 09:00:00 ¥1800 → ¥1700
- 📤 卖出 1 次，最高到 ¥2600
  · 08:00:00 ¥1700 → ¥2600

**蜃景**
- 📤 卖出 1 次，最高到 ¥1100

> 汇总时间：2026/10/31 00:00:30
```

**实现细节**：

- 用 `chrome.alarms` 每天 0:00 触发，触发后自动重排下一次，保证锚定在 0:00 而不是"每 24 小时漂移"。
- 汇总的是**刚结束的那一天**（0:00 触发时统计昨天）。
- 事件流水存本地，只保留最近 7~8 天，自动清理。
- 补货/卖出的**明细仍完整保存在「查询记录」表格里**，随时可查、可筛选、可导出。

> 前提：浏览器要开着。`chrome.alarms` 在浏览器完全关闭时不运行；如果 0:00 时浏览器没开，会在下次启动后补发（因为定时器会重排）。这是浏览器扩展的固有限制。

## 商品链接能直接打开了（v0.17.0）

之前的链接打不开，查到两个真实原因：

**1. 链接里带了 `refer_sn` 这个一次性会话参数**

从你机器上的记录看，149 条搜索页 URL 里有 **145 条带 `refer_sn`**（如 `refer_sn=01A18CEB-A03E-...`），每次访问都不一样。这是会话级令牌，过一会儿就失效，转发到微信里再点当然打不开，或者打开是一个空结果页。

现在所有链接都会**剥掉 `refer_sn` / `refer_page` / `traceid` / `spm` / `from`** 这类参数，只保留能长期访问的部分。

**2. 商品详情链接压根没抓到（`link` 全是 null）**

你机器上 81 条记录里 `link` 全为空，所以消息只能退回用整页搜索地址。原因是旧代码只取「卡片内第一个 `<a href>`」，而藏宝阁卡片的第一个链接常常不是商品详情。

现在改为按优先级找：

1. 你自定义的选择器
2. 卡片内**任何**形如 `/cgi/mweb/equip/1/<ID>` 的详情链接（这才是永久有效的商品地址）
3. 卡片 HTML 里嵌着的 equip 地址（兼容 `data-*` 属性）
4. 以上都没有，才退回普通链接

藏宝阁真实详情页形如：
`https://id5.cbg.163.com/cgi/mweb/equip/1/202610261903416-1-J7XEAGX9OZKOYF`
这条链接不带任何会话参数，任何时候点都能打开。

**另外**：企微消息里现在同时给「可点的文字链接」和「一行明文地址」，万一某个客户端把 markdown 链接吃掉了，你还能直接复制或点那行明文。

### 表格里也能直接点了

「查询记录」表格新增最右一列**商品**：

- 抓到了详情页 → 显示蓝色「打开商品」，点击新标签打开
- 只抓到搜索页 → 显示灰色「打开列表」（并提示这条没抓到详情）
- 都没有 → 显示 `—`

导出 CSV 里「商品链接」列也在，且同样已去掉会话参数。

## 补货 / 卖出不单独成条（v0.16.0）

补货和卖出**不单独记一条**，而是直接挂在对应那次询价记录上：

- **查询记录**：一行里同时有价格、目标价、以及 `🆕 补货 ¥2000 → ¥1800` 这样的变动标记。同一次查询不会出现两行。
- **企微消息**：同一轮里既补货又达标时，**只发一条**整合消息，不会收到两条内容重叠的通知。

合并后的消息长这样：

```
### 🆕 补货提醒（更便宜的上架了，且已达标）
**皮肤**：赤宴
**最新最低价**：¥1800（原 ¥2000，降了 200）
✅ 已达到你的目标价 ¥1900
**商品链接**：[点此查看](...)
```

如果只是补货、没达到目标价，就**不提目标价**，保持消息干净：

```
### 🆕 补货提醒（出现更便宜的）
**皮肤**：蜃景
**最新最低价**：¥900（原 ¥1000，降了 100）
**商品链接**：[点此查看](...)
```

只有"多个不同皮肤同时命中"这种情况，才会用分隔线把它们并列在同一条消息里。

## 补货 / 卖出提醒（v0.15.0）

除了"达到目标价时提醒"，现在还跟踪**最低价的变化**，自动判断市场发生了什么：

| 最低价变化 | 判断 | 推送标题 |
|---|---|---|
| **变低** | 有更便宜的上架了 | 🆕 补货提醒（出现更便宜的） |
| **变高** | 最便宜的那个被买走了 | 📤 卖出提醒（便宜的被买走了） |
| 不变 | 无事发生 | 不推送 |

**消息示例**：

```
### 🆕 补货提醒（出现更便宜的）
**皮肤**：赤宴
**最新最低价**：¥1800（原 ¥2000，降了 200）
✅ 已低于你的目标价 ¥1900
**商品链接**：[点此查看](...)
```

```
### 📤 卖出提醒（便宜的被买走了）
**皮肤**：赤宴
**最新最低价**：¥2500（原 ¥2000，涨了 500）
**说明**：之前 ¥2000 那个已经不在了，现在最低是 ¥2500
**商品链接**：[点此查看](...)
```

**关键细节**：

- **首次见到某皮肤只建立基线，不报事件** —— 避免一启用就刷出一堆"补货"。
- 价格差至少 1 元才算变化，防浮点抖动。
- 变动的基准是"上次看到的最低价"，不是"历史最低"。所以价格 2000→1800→2500 会依次报：补货、卖出。
- 推送失败会自动回滚记录，下一轮还能再报，不会永久漏掉。
- 只报**方向变化**，不重复轰炸：价格一直不动就一条都不发。

**在你的查询记录里怎么区分**：

- 类型列显示「🆕 补货」「📤 卖出」
- 结果列显示 `🆕 补货 ¥2000 → ¥1800`（绿色）或 `📤 卖出 ¥2000 → ¥2500`（橙色）
- 汇总行显示「补货 N 次、卖出 M 次」
- 新增「只看补货/卖出」筛选
- 导出 CSV 新增「变动事件 / 变动前价 / 价差」三列

## 触发风控时会怎样（v0.14.0）

一旦页面出现验证/拦截特征，扩展会**立即停止一切自动跳转**，并推送企微告诉你。

**识别范围**：
- 滑块验证（`#nc_1_wrapper`、`.nc-container`、`.geetest_panel` 等常见组件）
- 文字特征：拖动滑块 / 滑动验证 / 安全验证 / 人机验证 / 访问过于频繁 / 操作频繁 / 禁止访问 / 访问受限
- 验证码报错：验证码错误 / 已过期 / 失效
- 被跳转到登录页（登录态失效）

**触发后的动作**：
1. 停止定时器，不再跳下一个关键词（关键——避免把临时限制刷成更严重的封禁）
2. 写入查询记录：`⚠ 已暂停监控：<原因>`
3. 推企微：含原因、发生的关键词、当时的页面链接、恢复步骤
4. 弹本地通知
5. 在配置页顶部显示黄色横幅，附「打开当时的页面」和「我已处理，清除提示」

**恢复方式**：点开页面手动过验证 → 点扩展图标「监控当前页面」。重新启用会自动清除暂停标记；如果仍在验证页，会再次触发暂停（不会空转）。

**误报做了防护**：正常页面上常见的「登录」「获取验证码」「请勿轻信索要验证码」等字样不会被当成风控。这一点有专门测试覆盖。

### 关于"自动过验证码"

**当前没有做，也不建议做。** 原因：

1. 滑块验证码是**专门用来区分人与自动化的**。自动破解它在技术上属于绕过反爬措施，与"真人用浏览器"的定位直接冲突——一旦这么做，前面所有"我们不是爬虫"的性质就都不成立了。
2. 破解滑块需要图像识别 + 轨迹模拟，成本高、更新频繁，且一旦被识别，后果比不破解严重得多（可能直接封 IP 或账号）。
3. 从收益看：你要的是"便宜皮肤出现时知道"，而不是"抢在所有人前面 0.1 秒下单"。收到通知后你手动去买，完全来得及。

如果将来确实遇到频繁验证，正确方向是**降低触发概率**（减词、拉长周期、限定时段），而不是破解验证。这部分的取舍你可以再定，但我建议保持现状。

## 关于「是不是爬虫」

这个扩展**不是爬虫**。它不自己构造请求、不逆向签名、不带假 UA、不改 Cookie。所有页面加载都由 Chrome 正常发起，携带你真实的登录态，签名由藏宝阁自己的前端 JS 生成——和你手动点「下一页」在服务端看来没有区别。

爬虫风控针对的是「无签名 / 异常 UA / 高频连发」。这三条都不适用于当前实现。真正需要留意的只是**别让一个标签页在极短时间内连续跳转**，这也是下面自适应间隔要解决的问题。

## 皮肤会越来越多：自适应节奏（v0.13.0）

这是之前设计的隐患：轮内间隔固定 20~45 秒，皮肤一多就会出问题。

| 皮肤数 | 旧的固定 20~45 秒 | 现在（自适应） |
|---|---|---|
| 3 | 一轮 1~2 分钟 | 一轮 1 分钟（不拖慢） |
| 30 | 一轮 10~22 分钟 | 一轮 16 分钟 |
| 100 | 一轮 33~74 分钟，**超出周期** | 一轮 33 分钟，**正好落在周期内** |
| 300 | 一轮 100~225 分钟，周期彻底失效 | 会明确警告「一轮 1小时40分 > 周期」，提示你调大周期 |

**做法**：轮内间隔 = 「整轮周期 ÷ 关键词数」，再夹在 [你设的最小间隔, 你设的最大间隔] 之间。

- 词少 → 预算充足，用 20~45 秒随机（不无意义地拖慢）
- 词多 → 预算变小，自动收紧到接近下限，保证一轮跑得完
- 词极多 → 触到下限就**不再加速**（不会为了赶周期而冒风控风险），转而提示你调整配置

配置页底部新增「当前节奏预览」，实时显示：轮内间隔多少秒、一轮要多久、平均每个词多久查一次，以及是否超出周期。

### 皮肤变多后的建议

1. **优先调大整轮周期**，而不是压缩轮内间隔。3 个词半小时一轮很轻松；30 个词想半小时一轮，就是每 1 分钟查一次，意义不大。
2. **按重要度分组**：真正想抢的皮肤放一个清单、半小时一轮；长尾皮肤单独跑、几小时一轮。
3. **用时段控制**：夜里不做无谓查询。
4. 100 个词是当前配置（30 分钟周期）的上限；再往上请把周期调到 1~2 小时。

## 搜全清单 vs 风控：现在的节奏（v0.12.0）

**先说清楚旧逻辑的坑**：旧版是「**每个**关键词之间等 baseInterval」，不是「每轮等一次」。你有 3 个词、设 1200+300 秒，实际一轮要 **60~75 分钟**，不是 20 分钟。

新版把调度单位改成「**整轮**」：

| 参数 | 含义 | 默认 |
|---|---|---|
| 整轮间隔 | 所有关键词都搜完一遍后，等多久开始下一轮 | 1800 + 300 秒（30~35 分钟） |
| 轮内间隔 | 一轮里相邻两个关键词之间等多久 | 20~45 秒随机（下限强制 ≥15 秒） |

举例（3 个关键词）：
```
10:00:00  搜「于此岸赴宴」
10:00:30  搜「蜃景」        ← 轮内随机 20~45 秒
10:01:05  搜「赤宴」
10:31:05  搜「于此岸赴宴」  ← 整轮 30~35 分钟后开始新一轮
```

### 为什么这样不容易触发风控

公开实测的经验值是：**同一 IP 若请求快于约每 3 秒一次、连续几十次，会触发滑块验证**。所以真正危险的不是「一天查多少次」，而是「短时间内连发」。

新版在这一点上是刻意保守的：

- 轮内相邻查询至少间隔 **15 秒**（填小了也会被强制拉到 15 秒，防误设）；
- 每个间隔都在区间内**随机**，不是固定节奏；
- 整轮之间有 30~35 分钟的静默期；
- 3 个词 → 每小时约 6 次页面跳转，平均约每 10 分钟一次，远低于风控阈值；
- 时段控制仍然生效，可只在白天跑。

### 更进一步降低风险的三个办法

1. **减少关键词数量**：清单里只留真正想要的皮肤，词越少请求越少。
2. **拉长整轮间隔**：改成 3600+600（1 小时一轮）会更稳，代价是发现变慢。
3. **只在非高峰跑**：用「时段控制」设成凌晨或你常看的时间段。

> 注意：藏宝阁页面底部明确标注禁止爬虫，这条线要自己把握。当前配置是「模拟人偶尔翻页」的量级，不是采集器。如果被要求验证，手动过一次，不要继续加频率。

## 为什么之前日志很少 / 一次底价都没读到（v0.11.0 已修）

我从你 Chrome 的扩展存储里导出了实际记录，9 条**全部**是「未找到商品卡片」，没有任何价格。原因有两个：

**1. 页面是异步渲染，脚本扫得太早（主因）**

藏宝阁前端是 Vue 客户端渲染：HTML 先返回一个空骨架，商品卡片要等接口数据回来后才挂到 DOM 上。扩展在 `document_idle` 立刻扫描，此时卡片数量是 0，于是判定“没有商品”，记录「未找到商品卡片」并马上跳到下一个关键词。

现在改为**轮询等待卡片出现**（最多 12 秒，每 250ms 检查一次），卡片渲染出来后才真正读取价格。若超时仍无卡片，日志会明确区分「页面仍在加载」还是「选择器不匹配或被风控拦截」。

**2. 日志“断了 10 小时”，以及你早上看到的白页**

`00:56 → 11:30` 空白 10.5 小时，其间浏览器在 `01:11~01:23` 重启过。Chrome 的 Memory Saver 会把长时间在后台的标签页冻结甚至丢弃，页面变成白页，注入的脚本随页面一起消失，监控就此停摆——而且**不会有人告诉你**。

现在加了后台守护 `keepalive.js`（用 `chrome.alarms`，不依赖标签页存活）：

- 每 5 分钟巡检一次；
- 发现监控页变白（正文近乎为空 + 卡片 0 个）→ **自动重载**恢复；
- 发现找不到监控标签页，或超过 60 分钟没有新查询 → **推送企微 + 弹本地通知报警**；
- 同一问题 30 分钟内不重复报警，避免轰炸。

这样监控一旦停摆，你会立刻收到消息，而不是等到早上发现白页。

## 已修复的问题（v0.7.0）
- **popup「监控当前页面」必然报错**：manifest 移除了 `scripting` 权限但 popup 仍在调用 `chrome.scripting`，点击后抛异常。已补回权限并改用正确的 `registerContentScripts` / `updateContentScripts`（数组入参）。
- **通知弹不出来**：通知图标是一个只有 1×1 像素的占位 base64，且 `ICON` 变量被指向该内联图；已生成 16/48/128 真实图标并改为引用文件。
- **service worker 不回传结果**：`onMessage` 监听器没有 `return true`，异步 sendResponse 失效；已修复，并把推送成功/失败回传，失败时 content 侧自动回滚去重记录。
- **搜索关键词含 `%` 会崩**：`searchParams.get()` 已解码，代码又调了一次 `decodeURIComponent`，遇 `100%` 抛 `URIError`。已去掉重复解码。
- **最低价会把千分位读错**：`¥1,880` 被读成 `1`；已正确处理千分位逗号。
- **配置可能存成 NaN**：首次打开配置页「最低价目标」是空的，`parseFloat('')` → `NaN` 落库，兜底阈值失效。已改为统一数值校验 + 默认值回填，非法值拒绝保存并标红。
- **首次部署会静默不工作**：首次打开配置页时「关键词」输入框为空但校验只认关键词；现已在默认值里一并预填，与皮肤清单共用同一份数据。
- **配置改了不生效**：已打开的监控页原先只在重新加载后才用新配置；现在配置变更会自动刷新监控页。
- **选择器填错直接抛异常**：非法选择器异常会中断整轮监控；现在只告警一次并继续运行。
- **消息超长被企微拒收**：命中较多时消息会超过 markdown 4096 字节上限；现按字节切分多条发送。
- **费用/风控**：多条命中合并为一条消息，避免触发企微每分钟 20 条限流。

## 去重逻辑
- 套餐：`商品链接（缺省用账号标题+售价） + 命中皮肤名组合` 主键。
- 搜索（v0.20.1 起）：`search|item:商品身份|p价格档` 主键。
  - 商品身份 = 商品链接；链接取不到时退化为「标题 + 卡片文本（剔除价格）」，不同商品可区分。
  - 价格档 = 按 10 元取整，同一商品价格 ±5 元内视作“同一价格附近”，不重复提醒；跨档才再提醒。
  - 不同商品即使价格相同也各自提醒；同一商品反复刷新只提醒一次。
- 旧版搜索键为 `search|关键词|最低价`，且另用 `pm_best` 做“只在创新低时提醒”的闸门——这正是 v0.20.1 修复的漏报原因。
  旧键不再参与判重（视作无记录），也不会被删除，数量超过上限时随淘汰策略自然退出；`pm_best` 仅保留为日志展示。
- 存于 `chrome.storage.local.pm_notified` / `pm_best`，刷新/重开仍去重；点「清空已通知记录」两者一起清空。
- 推送失败会自动回滚去重记录，下一轮仍会重试，不会因为一次网络抖动就永久漏掉提醒。

## 注意事项
- `host_permissions` 为 `<all_urls>`，用于匹配任意站点与请求企微接口；仅本地自用。
- 网易藏宝阁风控严格，请勿把刷新间隔设得过短；若页面要求验证，先手动通过再继续。
- 搜索结果的卡片结构与首页一致（均用 `.product-item` / `.row-hd .price`）的假设已默认；若你实测最低价读不到，把搜索结果页的 HTML 发我，我按实际结构调整选择器。
- **排错看控制台**：选择器填错、读不到价格、找到 0 个卡片等情况，扩展会在页面控制台输出 `[价格监控] ...` 告警且不会中断（旧版会静默失败或直接抛异常），按 F12 打开控制台即可定位。
- **企微返回错误会显式提示**：企业微信即使出错也常返回 HTTP 200，扩展会检查 `errcode`；「发送测试消息」会如实显示失败原因，不再一律显示成功。
